  • 증상: GPU 코어 유휴, TTFT 증가, 처리량 저하
  • 원인: 메모리 대역폭/용량/파편화 한계
  • 대응: Paging, Caching, Quantization, IO-aware 알고리즘

Slide 5 · LLM 시대 위기

[LLM 시대] 새로운 위기, KV Cache 병목

  • 키워드: Auto-regressive Generation, KV Cache
  • 단어를 한 개씩 생성할 때마다 과거 문맥(K/V)이 VRAM에 누적
  • 요청 길이가 길어질수록 메모리 점유량이 가파르게 증가
  • 가변 길이 배치 요청이 VRAM 내부 구멍(파편화)을 빠르게 확대

핵심 포인트: 텍스트 생성이 길어질수록 사용 메모리와 낭비 메모리가 함께 커지며, 실제 처리량은 예상보다 먼저 무너진다.

시각화: VRAM 내부의 KV Cache 누적과 파편화

Step 1. 짧은 요청들 (초기)
Step 2. 긴 요청/배치 혼합 (중기)
Step 3. 파편화 심화 + OOM 임계 접근
초기 KV 블록 증가한 KV 블록 고밀도 + OOM 위험 파편화 구멍
왜 파편화가 문제인가? Step2 vs Step3
Step 2 여유 블록이 아직 있어 요청을 수용 가능하지만, 연속 공간 요구가 늘면 배치 효율이 떨어지기 시작
Step 3 총 여유량이 남아도 큰 연속 블록을 못 만들어 할당 실패 발생. 즉, "남은 메모리"와 "쓸 수 있는 메모리"가 분리됨

결론: 파편화는 메모리를 고갈시키기 전에 성능을 먼저 무너뜨리고, 임계점에서 OOM을 가속한다.

Slide 6 · 돌파구 1

[왼쪽] Transformer 한계와 vLLM

  • KV Cache 딜레마: 문맥이 길어질수록 메모리 부담이 급격히 커짐
  • 복잡도: O(N^2) 성향으로 긴 컨텍스트에서 비용이 빠르게 증가
  • 반창고 전략: PagedAttention(vLLM)으로 조각난 VRAM에 블록 단위 매핑
  • 효과: 파편화와 메모리 낭비를 크게 줄여 처리량을 실무 수준으로 회복
vLLM(PagedAttention) 시각화 · "테트리스"

상단: 기존 단편화 상태, 하단: 블록 재배치 후 높은 밀도

[오른쪽] Post-Transformer, Mamba(SSM)

  • "심장 교체" 전략: 아키텍처 자체를 바꿔 KV Cache 의존성을 낮춤
  • 복잡도: O(N) 선형 복잡도, 문맥 길이가 커져도 메모리 증가가 완만
  • 핵심 문장: 과거를 압축하다. 고정된 state로 정보를 누적 표현
  • 의미: 1만 토큰이든 100만 토큰이든 메모리 스케일링 안정성 확보
복잡도 비교 시각화
문맥 길이 Transformer(KV) Mamba(SSM)
8K 상대 메모리 1x 상대 메모리 1x
64K 상대 메모리 64x 수준 증가 상대 메모리 8x 수준 증가
1M 실무상 극단적 부담 (OOM 위험) 선형 증가 또는 사실상 일정에 가까운 거동

핵심 포인트: 태생적 한계를 소프트웨어(메모리 관리)로 완화한 vLLM과, 수학적 아키텍처 자체를 바꾼 Mamba는 서로 다른 레벨의 혁신이다.

핵심: vLLM은 반창고, Mamba는 심장 교체 - 두 혁신이 공존한다 06 / 09
